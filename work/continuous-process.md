# 从跨系统人工衔接转向连续流程
先定义完整旅程与系统交接点，找出断点，再定义最小连续流程，最后按序分段迁移。以下为可执行的工作流。  
步骤一：画出完整旅程与系统交接点  做什么：从报名到完成任务的全程画成一条线，标出每个系统以及系统之间的交接点。  怎么做：沿旅程逐站列出承载系统（邮箱、表单、多维表格、群聊、网站、证明流程等）；在每个交接点标注「谁把什么数据搬到哪里、用什么方式核对」。  产出与通过：得到一张旅程图和一份交接点清单；每个跨界动作都能在图上找到对应位置，没有「说不清在哪一步发生」的环节。  
步骤二：找断点  做什么：定位数据和状态靠人工搬运、核对、解释的地方。  怎么做：逐条检查三类症状——同一数据重复录入、状态无法在两侧同步、必须人工对账；把每个系统交界处需要「人工路由器」的点标为断点，并记下它带来的解释成本。  产出与通过：断点清单，每条写明症状、位置和后果；不把「给这段加个脚本」当成断点的解法。  
步骤三：定义最小连续流程  做什么：确定哪一段旅程必须先在同一个承载里连续跑通。  怎么做：选取报名、问卷、任务、交付、进度这条主线，定义它们共用的状态与数据字段；明确迁移后邮件、群和表格退回通知或档案角色，不再承担状态衔接。  产出与通过：一份最小连续流程说明，包含状态定义、字段清单和各系统退位后的角色；能画出一段从入口到交付不需要人工搬数据的路径。  
步骤四：按序分段迁移  做什么：把旧系统里的片段依次迁入连续承载，而不是继续给每个片段加脚本。  怎么做：按依赖顺序迁移——先让入口与身份数据连续，再迁任务与交付，最后迁进度与证明；每迁一段就验证该段不再需要人工对账，再进入下一段；迁移期间保留旧系统的通知与档案角色。  产出与通过：每段迁移都有验收记录，写明该段省掉了哪个断点；全部完成后，主线旅程在同一承载内可连续追踪。  
步骤五：自动化之前先定衔接  做什么：把「衔接已定义清楚」作为写自动化脚本的前置条件。  怎么做：只有当交接点的状态与数据字段已写定、且不再靠人解释时，才为动作加脚本或配置；衔接未定，先回到步骤一。  产出与通过：每个自动化动作都能对应到步骤三的状态定义；没有只为固化补丁而新增的脚本。  
边界  这是问题诊断与架构建议，统一工作台尚未上线，迁移方案需要通过后续项目验证。  提案原文只给出对「流程破碎」的诊断和连续化方向，本方案不声称某个系统或平台已经落地。  原始讨论上下文、实践状态与结果表述仍待核对；如有后续数据或制度版本，可补充后再作为成熟案例迁移。
